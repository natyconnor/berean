Passage Memory

Turn contiguous scope packs into a dedicated progressive-part loop: encode the next piece, recite a short recent chain, pass at 85% (not word-perfect), and keep ordinary hearted verses as independent memory cards.

Settled decisions

Decisions locked before implementation

Fixed constraints from the product owner plus defaults locked so implementers do not fork the model. Treat as non-negotiable.

Decision Resolution
Progressive part, not a verse queue A passage is a first-class object with a frozen piece list, a joined prefix, and a frontier. Pieces are not hearts and are not independent SRS items. Do not auto-heart a chapter in order to learn it.
Piece size Reuse groupChapterForHearting with empty existing hearts so user hearts never fragment the piece list. Same caps: MAX_GROUP_VERSES = 4, MAX_GROUP_WORDS = 60, sentence / heading / paragraph splits.
Independent hearts Hearting a verse inside a passage scope still creates a normal savedVerses + verseMemory card. Users can Learn / Review / Practice that heart on its own. Unhearting it does not change passage pieces. Passage progress never writes those rows (except the one-time migration unheart below).
Daily add budget Encourage at least one new piece per local day while building. Allow up to PASSAGE_MAX_ADDS_PER_DAY = 5 joins. Same-day adds are allowed; do not overnight-lock each piece. After a join, offer “Add another piece” vs “Done for now”.
Compressed frontier encode A piece can join in one session. Frontier ladder is Read (1) → Guided (2 first-letter reps) → From Memory of the piece (1 pass at ≥85%). Skip Challenge and skip the verse-memory overnight lock. The join recitation is the connecting recall.
Pass threshold Passage attempts pass at accuracy >= LEARN_PROGRESS_ACCURACY (85), same bar as verse Guided banking. Applies to frontier Guided, frontier From Memory, prefix continue, join, stall-repair clear, section-complete, and finished-passage review scheduling. Do not require exact to move on — long typed chains make word-perfect gating frustrating. Below 85% is a retry / stall, not a permanent day lock.
Sections + rehearsal window Large sections start at a new chapter or an ESV heading/subheading (grouping already splits pieces there). Building warm-up does not always start at verse 1: default rehearsal start is max(sectionStart, joinedCount - PASSAGE_REHEARSAL_MAX_PIECES) with PASSAGE_REHEARSAL_MAX_PIECES = 3, then trimmed so the window’s word count stays ≤ PASSAGE_REHEARSAL_MAX_WORDS = 120 (drop oldest pieces in the window first). Explicit actions: “From the start of this section” and “From the beginning of the passage” (no word cap — deliberate long practice). After the last piece of a section joins, offer a full-section recitation (optional). Finished passages review as the whole passage.
Stalls A failed prefix or join (<85%) is a stall, not a skip-to-next-card. Find the first non-typo error, map it to a piece, cue with the end of the previous piece plus first letters of the stalled piece, then retry from one piece earlier. After a successful repair (≥85%), continue the interrupted flow (prefix → frontier encode when adds remain; join → retry join). Prefix failure must not lock out adding for the rest of the day — repair then continue into the new piece. Join passes at ≥85%, not exact.
Speaking mode Out of scope. Typed recall (existing textarea + word diff) remains the only input, including long prefix recitations. Do not add mic / speech APIs.
Who becomes a passage Eligible: kind === "scope", contiguous chapters in one book ( scopeChaptersAreContiguous), chapter count 1–20 (AUTO_HEART_MAX_CHAPTERS). Custom packs, tagged whole-corpus scopes, multi-book scopes, and over-cap ranges stay heart collections. Schema kind stays "scope" | "custom".
Migration of auto-hearted packs Lazy, idempotent materializePassage on pack open and before a pack session (including a global unified pack card). Compute canonical pieces (empty hearts). Infer joinedCount as the longest prefix of pieces whose every verse is covered by a heart in review/mastered. If looksLikeAutoHeartedPassage (full scope coverage, heart count equals piece count, every heart span equals a piece), unheart those matching spans using the existing unheart path (keep verseMemory history). Keep any heart that does not exactly match a piece (user-shaped, e.g. John 3:16 beside a 16–17 piece). Clear unifiedReviewEnabled. Show a one-time banner with unheart/keep counts. Never regroup pieces after materialize.
Unified recitation Keep setUnifiedReview / recordUnifiedReview as fallback for unmigrated packs. Migrated packs review through passageMemory (one schedule on the passage row). Do not delete unified code in this plan.
Global queues Building passages appear in Learning (one card), not as N verse cards. Reviewing passages appear in Review as one card, like today’s unified pack item. Remaining hearts in the scope stay visible as individual due verses — do not hide them once the passage exists.

Shared architecture

Data model & core contracts (referenced by every PR)

Mental model

A heart is still a user-chosen verse (or short span) in savedVerses with its own verseMemory ladder. A passage is a contiguous scope pack the user is memorizing as one growing recitation. Pieces are derived groupings of that scope, stored on the passage row, never as hearts. Joined prefix = pieces [0, joinedCount). Frontier = pieces[joinedCount] while building. Unreached pieces are visible on the map and must not enter any learning queue.

Due-queue integration

Extend dueQueuePackItem (keep kind: "pack") with optional passageStatus and members sourced from passageMemory.pieces when a row exists. Building passages are not review-due; they increment memoryStats.learningDue by 1 when a session is available today (always, while building, except when the only work left is adding and remainingAdds === 0 — then they are done until the next local day, still offering prefix practice from the pack). Reviewing/mastered passages use isDueForReview on the passage row and count as 1 in due.

After materialize, that pack must not contribute members to unifiedReviewPhaseVerseRefIds (flag is cleared). Leftover hearts stay in the verse due scan.

Global Learning currently filters savedVerses.listAll. Add building passage cards to the learn page the same way Review already merges pack cards: either extend a learning queue query or have the learn page also read packs.listMine / passageMemory by user. Prefer a small verseMemory.learningQueue (or passageMemory.dueForLearning) that returns building passages with a session available today, rather than stuffing them into listAll.

Unheart helper

Extract the remove-branch of savedVerses.toggle into unheartByVerseRefId(ctx, userId, verseRefId, now) in convex/lib/savedVerses.ts (or convex/lib/verseMemory.ts next to deletePackMembershipsForVerse). Both toggle and materialize call it. Stats, isHearted, membership cleanup, and “keep review history” stay identical.

Data flow

User creates or opens an eligible scope pack. The client fetches chapter text via getChaptersBatch (session cache), builds pieces with buildPassagePieces, and calls passageMemory.materialize. That row is now the source of truth for the pack’s passage loop. A Learn session runs reducePassageSession: recite the short rehearsal window (typed composite text, last ≤3 pieces / ≤120 words), encode only the frontier piece with the compressed ladder, recite window + new piece, and on a ≥85% join call joinNextPiece. Independent hearts in the same chapters keep their own recordAttempt path. When joinedCount === pieces.length, Review presents one composite card of every piece; recordAttempt({ kind: "review" }) runs scheduleNext on the passage row only (pass at ≥85%). Opening an old auto-hearted pack follows the same materialize path once; matching hearts disappear from the library, leftover hearts remain, and unified mode turns off.

Convex and product rules

  • Every public query/mutation has args and returns validators.

  • Never call Date.now() inside a query — pass now in. Mutations may use Date.now() for createdAt.

  • No any; use generated Doc<> / Id<> types.
  • Do not create hearts when materializing pieces. Do not hide leftover hearts from the due queue after materialize.
  • Do not add speech/mic UI. Do not regroup frozen pieces.
  • Custom packs and ineligible scopes must keep today’s heart-member behavior.
